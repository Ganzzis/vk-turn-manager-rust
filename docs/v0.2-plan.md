# VK TURN Manager v0.2.0 — implementation plan

Status: design proposal; **not implemented**. v0.1.0 remains the production-tested baseline.

## Verified baseline

Ubuntu 26.04: WireGuard `wg-vk` UDP 51820, DTLS-SRTP UDP 56004, client 10.240.42.2/32, outbound interface `ens3`. Internet access required IPv4 forwarding and nftables masquerading; services and nftables rules survived reboot. These are observations from manual VPS testing, **not** a guarantee for other hosts.

## Scope and proposed CLI

- `network plan`: read-only checks of outbound interface, WG address/subnet, forwarding state, nftables availability and existing rules. Print changes; no mutation.
- `network enable`: explicit opt-in; create only uniquely named, managed nftables table/chains, persistent systemd unit and managed sysctl configuration. Refuse conflicts and unknown existing ownership.
- `network status`: report forwarding, nftables rule presence, service state and mismatches.
- `network disable`: remove only owned resources; restore prior forwarding setting only when it can be done without disrupting another user.
- `client add <name> --vk-link <url>`: generate client WG keypair, allocate a free tunnel IP, add peer to active WG and persisted configuration atomically, create private local client profile and an import link compatible with the **verified** iOS schema. No private key in stdout or logs.
- `client list`: show name, address, peer public key and handshake, never secrets.
- `client revoke <name>`: remove the peer from both runtime and persistent configuration; require confirmation or explicit flag.
- `client export <name> --output <path>`: write import link to an owner-only file; refuse stdout by default.

## Safety requirements

1. No mutation of default nftables tables, global firewall policy, SSH rules or unrelated systemd services.
2. Check existing UFW/nftables forward hooks: an `accept` in a separate base chain cannot override a `drop` elsewhere.
3. Validate detected egress interface and subnet; do not hard-code `ens3` or `10.240.42.0/24`.
4. Enforce exclusive lock, root-only permissions on secret-bearing files, atomic writes, and rollback on failure.
5. Do not print WireGuard private keys, full client URLs, connection payloads, or tokens to CI output. Prevent accidental commits of secret files.
6. Never silently overwrite operator-edited WG configs; detect drift and require reconciliation.
7. Existing v0.1.0 installs must not be removed/reinstalled as part of upgrade; introduce explicit migration.
8. Avoid storing VK call links in public code or tests. Use synthetic fixtures.
9. `uninstall` must not delete externally created nftables rules or restore system-wide forwarding if other workloads need it.

## iOS link format verification

The earlier manually generated `vkturnproxy://import?data=...` payload used a `type=connection`, `version=1`, `settings` JSON object encoded as base64url. Before implementing an exporter, confirm this schema against the actual iOS client implementation or a reproducible import test. A successful VPN session does not by itself prove all schema fields are correct. Avoid embedding client private keys in QR images stored in CI artifacts.

## Delivery stages

1. Network read-only diagnostics and unit tests.
2. Explicit network enable/disable with ownership metadata, rollback, and reboot test.
3. Peer management and persistent config update with tests for duplicates, conflicts and rollback.
4. iOS exporter with validated schema and secret-safe file output.
5. Upgrade path, CI and security checks; real-device regression on Ubuntu 24.04 and 26.04.

## Acceptance tests

- Existing v0.1.0 service and iPhone connection continue working after upgrade.
- Fresh VPS install + network enable + client add + iOS import yields successful internet access.
- Reboot preserves forwarding, NAT, both services and peers.
- Repeated enable/disable is idempotent; foreign firewall rules remain untouched.
- Failed installation/upgrade rolls back owned changes only.
- No private keys or credentials appear in Git commits, logs, PR artifacts, or diagnostic output.
